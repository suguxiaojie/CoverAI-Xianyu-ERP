# 在线聊天与账号自动任务

## 在线聊天

进入“在线聊天”后，顶部按账号显示 Tab；每个账号拥有独立的会话列表和消息状态。下方是标准两栏布局：左侧为会话列表，右侧为当前会话消息窗口。

聊天功能包括：

- 会话联系人、头像、昵称、用户 ID、商品摘要和未读数；列表按闲鱼会话最后消息时间倒序。
- 进入会话后优先读取本地缓存，再从闲鱼历史消息接口补齐记录；底部可继续加载更早消息和更多历史联系人。
- 文本消息、闲鱼文字表情和图片发送。当前不支持从管理后台发送视频，因此界面不提供视频发送按钮。
- 发送方按“对方/我”区分，并显示对应头像；账号之间的会话和实时消息完全隔离。
- 应用使用后端 `/api/v1/chat/ws` 推送实时事件；刷新或重连后仍以历史接口和本地数据库为准，不只依赖 WebSocket 存续期间收到的消息。

### 官方消息识别

闲鱼的交易卡片和平台通知不能当作普通用户消息处理。当前按协议元数据识别：

- `contentType=14`：平台通知类消息；
- `contentType=26`：交易卡片；
- 发送方用户 ID `1400`：闲小蜜；
- “发来一条新消息”：官方通知占位内容。

识别出的消息不会进入关键词、默认回复或 AI 回复链，并在聊天窗口中以居中的系统消息卡片展示。实时 WS 收到 `contentType=14/25/26` 后会立即持久化并向管理后台广播，历史消息刷新只负责幂等补偿，不再作为交易卡片的正常显示路径。联系人分页返回的空会话壳不会导入列表，避免出现只有“暂无消息”的伪联系人。

如果昵称或头像缺失，点击会话列表刷新按钮；系统联系人闲小蜜使用平台头像和固定名称，不应把订单卡片标题当成用户昵称。

### 待付款订单修改价格

归属当前卖家账号、携带明确订单号和 `adjust_price` 动作的“我已拍下，待付款”交易卡片会显示“修改价格”按钮。点击后，系统先通过当前账号 Cookie 读取闲鱼返回的动态改价表单，再按返回顺序显示可编辑和只读字段；不要假设平台永远只返回商品价格与运费两个字段。

- 金额最多保留两位小数；商品价格必须大于 0，运费等其他金额字段可以为 0。
- 提交前必须再次确认，因为确认后会真实修改买家待付款订单；服务端会重新读取一次表单，避免使用已经过期的价格或字段。
- 元金额只在服务端转换为整数分字符串，不使用浮点数参与平台请求。
- 只有仍处于待付款状态、属于当前账号且尚未出现付款、关闭、发货、完成或退款终态的订单允许改价。
- 同一订单的付款、关闭、发货、完成或退款卡片到达后，原待付款卡片仍保留在历史位置，但“修改价格”按钮立即置灰并显示具体原因；即使前端尚未收到终态，服务端和平台 render 仍会在提交前做最终拒绝。
- 账号、订单和目标金额组成持久化幂等记录；同一目标价格已经成功、执行中或结果待核对时不会重复提交。
- 平台明确返回 `success=true` 后，卡片按钮显示“已修改价格”；网络中断、超时或响应无法判断时进入人工核对，不自动重放。
- Cookie 锁只用于取得当前凭证快照和协调响应 Cookie，不会跨越闲鱼网络请求；扫码登录或续期产生的新一代凭证不会被旧响应覆盖。
- 如果权威 Cookie 快照中的 `_m_h5_tk` 已缺失或过期，系统会在改价业务请求尚未发出时执行一次官方 token bootstrap，保存新 Cookie 后再重试；明确 Session 失效时停止并进入登录恢复，网络或业务结果不明确时绝不借此重复 submit。
- 改价采用单一应用弹窗的“编辑 → 确认 → 提交中 → 成功／失败”流程，不调用浏览器原生确认框。无金额变化时“下一步”置灰；确认页逐项展示当前金额、修改后金额和买家应付，只有“确认改为 ¥金额”按钮会执行真实 submit。

### 卖家取消未付款订单

卖家视角的当前会话如果恰好只有一笔仍未出现终态的未付款订单，会在聊天标题栏、“账号在线”左侧显示白底红字的“取消订单”。历史交易卡片不再重复显示取消入口；“修改价格”继续保留在原待付款卡片。买家账号收到同一平台广播时不会显示卖家操作。

- 打开弹窗时调用闲鱼 `order.close.reason.get` 动态读取原因，不硬编码原因；选择后第一次“下一步”只进入应用内确认页。
- 确认页明确说明取消后买家无法继续付款；只有红色“确认取消订单”调用内部卖家关单协议 `trade.close.by.seller`，不会尝试买家 cancel 接口。
- 服务端要求当前用户拥有卖家账号、卡片发送者不是该账号自身、订单仍是未付款，且后续没有付款、关闭、发货、完成或退款终态。
- 提交前重新读取平台原因并再次检查本地终态；选择已从平台列表移除时返回“关闭原因已失效”，不调用关单。
- 同账号同订单复用 `order_close:<账号>:<订单>` 持久化幂等键；成功、处理中或结果待核对时不能重复提交。
- Session 明确失效允许登录恢复；超时、断网或其他远端结果不明确时进入 `needs_review`，禁止自动重放。
- 闲鱼没有“每个新订单必建新会话”的官方规则，真实数据库也存在同一 `chat_id` 关联 2～4 个订单的情况。因此顶部入口仍按精确订单号去重；候选不是恰好一笔时隐藏，绝不猜订单。
- 买家付款后，顶部“取消订单”立即隐藏，卡片“修改价格”置灰。已付款退款、已发货售后不属于本功能。

## 账号自动评价

入口为“账号管理 → 账号自动任务”。自动评价是账号级开关，不针对不同买家配置不同文案：

1. 开启“自动评价”；
2. 填写统一好评文案，最多 500 个字符；
3. 保存后，后台持续扫描该账号的待评价订单；
4. 每个待评价订单按交易订单 ID 幂等执行，已经处理过的订单不会重复评价。

它不是每日任务。可以点击“立即评价”执行一次扫描，也可以依赖后台持续扫描。账号停用或暂停时不会执行。

## 每日自动擦亮

每日擦亮同样是账号级开关，但与自动评价不同：

- 按北京时间判断执行时间；
- 每个账号每天最多执行一次；
- 默认执行时间为 `03:00`，可在 `HH:mm` 范围内调整；
- 后台调用商品列表接口并逐个执行擦亮；当前实现按每页 20 条、最多 20 页读取商品；
- 可以点击“立即擦亮”手动触发，但当天已成功执行时会被幂等保护跳过；
- 页面会显示最近完成时间、本次发现数量、成功数、失败数和跳过数。

如果执行中部分商品失败，任务会记录失败原因并进入可重试状态；不要仅根据按钮返回就判断所有商品都已成功，应该查看本次执行结果。

## 订单生命周期状态

订单中心和聊天交易卡片共用同一套状态语义，前端不再根据中文文案自行猜测：

- `shipped`（已发货）：卖家已经发货；
- `received`（已收货）：平台明确记录买家确认收货，不等于物流签收；
- `completed`（已完成）：平台明确记录交易成功或交易完成；
- `refunding`（退款中）：存在精确订单号的退款申请事实；
- `refunded`（已退款）：平台明确退款成功或钱款原路退回；
- `cancelled`（已取消）：未付款取消或与退款无关的普通交易关闭。

订单详情分别展示 `paid_at`、`shipped_at`、`received_at`、`completed_at`、`refunded_at` 和 `cancelled_at`。只收到“交易成功”时不会反推买家主动确认收货；只收到物流签收信息也不会写 `received_at`。

实时 `refund_requested` 卡片会把精确订单转为退款中。没有订单号的“退款成功，钱款已原路退返”只在同账号同会话恰好一笔退款中订单时关联，多笔时只展示聊天消息而不猜订单。默认增量同步除新订单安全回看外，每个账号还会轮转补查最多 20 笔最久未更新的已发货、已收货或已完成订单；真正已退款和普通已取消订单不重复请求详情。旧版本已经压成已取消、但存在精确退款申请卡片的订单也会进入补查，并在通用关闭码下纠正为已退款。

双账号管理时，同一订单号可能已经归属另一个本地账号，包括已经逻辑删除但主键仍保留的历史订单。订单发现会逐条隔离这类冲突：保持既有所有者、统计“跨账号冲突跳过”，并继续写入同批其他订单，不能因一个冲突订单让整个账号失败。全量模式也会补查“已取消但存在精确退款申请证据”的历史订单，不再完全依赖订单列表批次成功；这类明确退款纠正独立于普通增量售后轮转的 20 笔上限，始终优先加入详情目标。完成进度同时显示账号和详情维度；worker 正常结束但业务有失败时明确显示“部分完成”，不能只看 `status=succeeded` 判断全绿。

订单列表的“买家信息”优先展示闲鱼昵称，买家 ID 作为次要稳定标识保留，收货人姓名继续单独展示，不能互相冒充。昵称只复用本地聊天会话：先匹配同账号精确 `chat_id`，再按同账号＋`buyer_id` 选择最近非空昵称／头像；缺失时显示“未获取昵称”和买家 ID，不批量请求平台。订单搜索同时匹配已有聊天昵称。

## 手动求买家送小红花

订单中心的订单详情对已付款、已发货、已收货和已完成状态提供“求买家送小红花”按钮。该按钮调用闲鱼官方订单求花动作，由平台向买家生成系统卡片，不是发送一条伪装成系统消息的普通聊天文本。

- 点击后必须再次确认；确认即代表会向真实买家产生平台消息。
- 服务端使用账号和订单组成的幂等键，同一订单成功求花后不能重复发送。
- 订单详情每次打开都会读取该幂等运行的持久状态；成功、处理中或待核对时按钮保持禁用，关闭弹窗或刷新页面不会恢复为可点击。
- 平台明确受理后立即显示“系统卡片同步可能需要几分钟”，不要用聊天卡片是否已经出现判断动作是否成功。
- 只有存在可靠付款时间且付款未超过 30 天的订单允许请求；缺少付款时间时先同步订单。
- 平台返回明确失败时允许人工修正后重试；网络中断等结果不明确场景进入人工核对，禁止自动重放。
- 平台调用期间不会持有账号凭证锁；返回后只有凭证代次未变化才协调响应 Cookie，避免覆盖同时发生的扫码登录。
- 手动求花与自动求花共用 `red_flower_request:<账号>:<订单>` 幂等键；无论从哪个入口先成功，同一订单都不会再次发送。

聊天历史与实时消息会把 `want_red_flower`、`sys_want_red_flower` 和 `received_red_flower` 相关卡片归一为求花、平台提示、已送花和已收到四类稳定事件。平台自动提示可能使用 `contentType=25`，其他小红花交易卡片通常使用 `contentType=26`。

### 自动求花与自动收花

“账号管理 → 账号自动任务”提供两个相互独立、默认关闭的小红花开关：

- **自动求小红花**：自动发货运行、人工完整发货或人工确认发货明确成功并写入 `shipped_at` 后创建持久化秒级任务。默认等待 10 秒，可设置为 `0～3600` 秒；超过付款 30 天、已退款、已取消、缺少发货时间或发货结果待核对的订单不会调用平台。
- **自动收小红花**：检测到实时 `red_flower_sent` 卡片后，用当前账号 Cookie 打开固定闲鱼官方收花页。默认显示独立 Chromium 窗口，也可以切换为无头模式；平台结果等待时间可设置为 `30～600` 秒，默认 120 秒。

自动求花沿用手动求花的订单幂等键。正常链路由现有每秒调度器领取，分钟扫描只补偿进程重启、漏掉的发货回调和明确失败后的安全重试。平台明确失败时按任务重试时间处理；超时、断网或其他无法确认远端结果的错误直接进入 `needs_review`，禁止自动重放。平台明确成功后才写入成功终态，并协调响应 Cookie 到数据库和在线账号。

平台部分“你已发货”卡片不携带订单号。系统只在同账号、同会话、已付款、未取消、未退款、尚无 `shipped_at`、付款早于发货且二者间隔不超过 24 小时，并且候选订单恰好只有一个时关联订单；0 个或多个候选都只展示卡片，不猜测订单，也不触发求花。

账号任务设置保存成功后会显示绿色“设置已保存”提示和当前秒数，保存按钮变为“已保存”并阻止重复提交；任意字段再次修改会清除成功提示并恢复保存按钮。

自动收花不复用账号持久化浏览器 Profile，不持有凭证锁等待页面，也不产生鼠标或键盘输入。同一账号的收花页面严格串行，不同账号最多由两个 worker 并行处理。打开页面、页面关闭或导航成功都不等于已经收花；只有同账号、同会话后续收到 `red_flower_received` 才写入成功。超时、导航后异常或进程在外部动作期间中断都进入人工核对，避免重复领取。

自动求花和自动收花终态复用账号任务运行记录与通知去重链路。账号停用、暂停或相应开关关闭时不会开始新动作；服务重启会先隔离上次进程遗留的 `running` 小红花任务。

### 手动收花

买家送花产生的 `red_flower_sent` 卡片在存在明确数字订单号时仍显示“立即收花”，作为自动收花关闭、失败或需要人工核对时的手动入口。点击后先由 ERP 二次确认，再打开固定的闲鱼官方 `red-flower-play` 页面；ERP 不直接调用需要 WUA 的安全收花接口，也不代替用户确认奖励。

- 官方 URL 的域名和路径由前端常量固定，平台卡片不能覆盖；订单号只作为编码查询参数。
- 非数字、缺失或异常长度的订单号不会生成收花按钮。
- 打开后按钮显示“重新打开收花页”，提示用户必须在闲鱼官方页面完成操作。
- 同一会话后续出现 `red_flower_received` 时，最近一条尚未完成的送花卡片自动显示“已收花”并永久禁用。
- 历史数据库中已有 `red_flower_sent + order_id` 但动作字段为空的记录，会在应用转换边界安全补齐官方收花入口，无需重新抓取历史。
- 页面跳转不等于收花成功，只有闲鱼推送的 `red_flower_received` 才是最终状态依据。

## 与交易自动化的边界

“账号自动任务”处理自动评价、每日擦亮、自动求花和自动收花；“自动化规则”处理可配置的订单和聊天触发业务规则：

- 付款后自动发货；
- 评价后发送赠品；
- 超时未评价求评价；
- 关键词回复、默认回复和 AI 回复。

闲鱼官方系统消息只用于平台事件识别，不应被配置为普通买家关键词触发自动回复。
